# 用例格式规范

表头固定为：

`分组 | 标题 | 等级 | 前置条件 | 步骤 | 预期结果 | 类型 | 备注`

格式要求：

1. `前置条件` 使用自然编号：
   `1. xxx`
   `2. xxx`
2. `步骤` 使用方括号编号：
   `[1] xxx`
   `[2] xxx`
3. `预期结果` 使用方括号编号：
   `[1] xxx`
   `[2] xxx`
4. `类型` 与 `备注` 没有信息时可留空。
5. 不要把“步骤”和“预期结果”混写在同一列。

语义要求：

1. 用例必须是可执行 case，不是需求描述。
2. 前置条件必须给出具体样本，例如账号A、账号B、车辆V1、时间60秒、守护人数0。
3. 步骤必须明确执行者、入口、对象和动作。
4. 预期结果必须明确可判定，涉及数量必须给出具体数值。
5. 合用例必须明确组合输入和聚合输出，例如：
   - 输入：账号A进入监控单车，账号B进入远遥Web，账号C进入Unity远遥
   - 输出：车辆V1守护人数=3
6. 未确认规则可以临时写入用例 `备注` 供评审，但不能写入 `knowledge/` 或导入知识库；必须先找用户强制确认。
7. 用例必须讲人话，直接写测试人员能照做的页面动作和页面结果：
   - 不写：`鼠标hover起点S0`
   - 应写：`将鼠标移入进度条上的起点标记“仓库A”`
   - 不写：`hover S0展示起点S0名称`
   - 应写：`页面展示站点提示浮层，浮层文案为“起点：仓库A”`
8. 不允许在步骤和预期中直接使用未解释的技术缩写、状态码、元素代号或半中半英表达，例如 `hover S0`、`click icon`、`status=online`。如果确实要用代号，必须在前置条件中映射到真实业务名称，步骤和预期仍优先使用真实业务名称。

文件位置要求：

1. 每个需求必须使用独立专题名目录：`workspace/<专题名>/`。
2. 原始需求放在：`workspace/<专题名>/original_requirement/`。
3. JSON 草稿放在：`workspace/<专题名>/test_case/cases.json`。
4. Excel 输出放在：`workspace/<专题名>/test_case/excel/cases.xlsx`。
5. 需求确认结论和稳定规则放在：`workspace/<专题名>/knowledge/`。
6. 未确认问题不允许放入 `knowledge/` 并落库；发现未确认问题时先停止落库并向用户确认。
7. 待确认问题放在：`workspace/<专题名>/original_requirement/open_questions.to_confirm.md`。
